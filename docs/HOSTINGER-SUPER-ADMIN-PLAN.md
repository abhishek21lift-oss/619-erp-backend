# Hostinger Super Admin — implementation plan

**Status:** built (2026-10-17). Audit findings and the constraint set that shaped it are below.

## 1. What this is

A Hostinger control surface **inside** the existing Platform Owner Command Center
(`/platform?tab=hosting`, module `operations`). Not a new app, not a new module
(the frontend pins `MODULES.length <= 8` in `platform-modules.test.ts`).

It connects to the **official Hostinger API** with a platform-owner token, stores
that token **encrypted at rest**, and exposes a curated allow-list of real API
operations with an approval gate for destructive ones, audit on every call, and an
AI assistant that can propose but never execute.

## 2. Ground truth for the API, and what it does NOT cover

Source: `https://developers.hostinger.com/openapi/openapi.json` (OpenAPI 3.0,
`info.version 2.1.0`, 325 paths / 412 operations). A slim snapshot of every
operation this module exposes is committed at `src/lib/hostinger/spec.json` and
regenerated by `scripts/hostinger-extract-spec.js`. The parity test inside
`src/__tests__/hostinger.catalog.test.js` asserts **every catalogue entry exists
in the spec with the same method and the same declared parameters**, so an
invented endpoint fails the build.

Verified capabilities used:

| Need | Endpoint(s) | Notes |
|---|---|---|
| Hosting accounts & websites | `GET /api/hosting/v1/websites`, `/onboardings`, `/orders` | websites are per-account (`username`) |
| SSL | `GET .../websites/{domain}/ssl/status`, `POST .../ssl/setup`, `PATCH .../ssl/https-redirect/toggle` | install + redirect are mutations |
| Website files | `GET .../domains/{domain}/files`, `.../files/content`, `POST /api/hosting/v1/files/upload-urls` | hosting only |
| Node.js apps | builds, build logs, runtime logs, settings, vulnerabilities, restart | deployment surface for Node apps |
| Git deploys | auto-deployment settings, `POST .../git/repositories/deploy` | |
| Domains | `GET /api/domains/v1/portfolio`, `/{domain}`, `/{domain}/renewal`, transfers | |
| DNS | `GET/PUT/DELETE /api/dns/v1/zones/{domain}`, snapshots + restore | |
| VPS | `GET /api/vps/v1/virtual-machines`, details, **`/metrics`**, `/actions` | real server health |
| VPS lifecycle | `start`/`stop`/`restart`/`recreate`, recovery mode, hostname, nameservers | restart & recreate are destructive |
| Docker | `/virtual-machines/{id}/docker` — list projects, contents, containers, **logs**, create/start/stop/restart/update/down | official Docker Manager |
| Backups | `GET /backups`, `POST /backups/{id}/restore`; snapshots create/restore/delete | restore is destructive |
| Billing | `GET /api/billing/v1/subscriptions`, payment methods, catalog | auto-renewal enable/disable |
| Firewall | list/details, create rule, activate/deactivate, delete rule | |

**Not supported by the official API, therefore reported `unavailable` with a reason
rather than faked:**

- **SSH terminal / arbitrary command execution on the VPS.** There is no exec
  endpoint in the spec. The UI shows the capability as unavailable and names the
  reason. The separate in-repo path for container restarts is the Command Center's
  allow-listed docker socket proxy (documented D6, still open on the live compose)
  — this module does not open a second one.
- **VPS file manager** — `files/*` endpoints exist for *hosting*, not VPS.
- Anything else the spec does not declare.

## 3. Architecture (reuse-first)

Backend is Express 4 + raw `pg` (not NestJS/Prisma), so the module follows the
platform-plane convention:

```
src/modules/platform/super-admin/hostinger.js      adapter: routes, zod, audit   (no SQL)
src/modules/platform/hostinger/credentials.service.js   encrypted store + verify/rotate/revoke
src/modules/platform/hostinger/operations.service.js    plan → confirm → execute, dashboard, history
src/modules/platform/hostinger/assistant.service.js     NL → answer | proposal (never executes)
src/lib/hostinger/{client,catalog,crypto,spec.json}     API client, allow-list, AES-GCM
src/db/migrations/229_hostinger_integration.sql         2 tables, deny-all RLS
```

Mounted with `router.use(require('./super-admin/hostinger'))` so it inherits the
existing `PLATFORM_GUARD`:
`auth → requireSuperAdmin → requireSuperAdminMfa → requirePlatformOwner` plus
`runAsPlatform()` for the owner connection. **No second door.** Tenant roles can
never reach these paths, and the existing guards already refuse impersonation
sessions.

## 4. Security model

| Requirement | Implementation |
|---|---|
| Token never reaches the browser | Only the mask (`…3f9a`), a SHA-256 fingerprint prefix, and timestamps are serialized. There is no endpoint that returns the token. |
| Encrypted at rest | AES-256-GCM, random 12-byte IV, envelope `v1.<iv>.<tag>.<ct>` in `platform_hostinger_credentials`. Key from `HOSTINGER_TOKEN_KEY` (32 bytes b64/hex). Malformed key in production refuses boot. |
| Masked credentials | `maskToken()` → `hg_…4f2a`; fingerprint lets an operator see "same token re-entered" without seeing the token. |
| Rotation / revocation | `POST /credentials/rotate` (new token verified against the live API **before** it replaces the stored one), `DELETE /credentials` (revoke). One active credential enforced by a partial unique index. |
| RBAC | Inherited `PLATFORM_GUARD`; every route is platform-owner only. Credential routes additionally require MFA (already part of the chain). |
| Audit | The credential lifecycle, every plan / execute / deny, every deliberate read operation and every assistant question → `activity_log`, `action = hostinger.*`, with the operation id, the outcome and the actor. Failures and refusals are recorded. High-frequency reads (status, catalogue, dashboard, tables) are not audited — see the adapter's header comment for why. |
| AI never sees secrets | The assistant prompt is built from the catalogue + scrubbed read results. `scrubBounded()` runs over every upstream string, and the token is passed to it as a known secret so even an unlikely echo is redacted. |
| SSRF | There is **no** user-supplied URL, host, or proxy parameter: the base URL is a module constant and cannot be set by env. Path parameters are validated (`username`, `domain`, numeric ids) and `encodeURIComponent`-ed; a `..`, `/`, or full URL is rejected by schema before the client sees it. |
| Rate limits | Two layers: our own express limiter (`makeStore('hostinger')`) for abuse, and a client-side pacer that respects Hostinger's documented 90 req/min with `Retry-After` handling, bounded fan-out and a short TTL cache so one dashboard load does not burn the budget. |
| Destructive gating | Catalogue declares `read` / `mutate` / `destructive`. `mutate` + `destructive` require a stored plan; `destructive` additionally requires typing the operation id. Reads may execute directly. Enforced server-side, tested. |

## 5. Database (migration 229)

- `platform_hostinger_credentials` — one active row (partial unique index), deny-all
  RLS + FORCE (same shape as `platform_owners`, same reasoning: the API reads it
  over the owner connection, `app_tenant` must never see it).
- `platform_hostinger_approvals` — plan → approve → execute, fingerprint over the
  resolved params, TTL, single-use (`consumed_at` claimed atomically).
- Operation history reuses `activity_log`. No third table.

Both tables registered in `src/architecture/domains.js` (`platform` domain) and in
`NO_TENANT_COLUMN_BY_DESIGN` with the reason, or the convention tests fail.

## 6. Frontend

New tab `hosting` in the `operations` module (`?tab=hosting`), lazy-loaded like
every other panel, split into three components:

- `hosting-centre.tsx` — connection/credential card (connect, verify, rotate,
  revoke), KPIs, website/SSL/domain/DNS tables, operation history.
- `hosting-vps.tsx` — VPS list + detail (metrics, Docker projects/containers/logs,
  backups, snapshots), destructive actions behind typed confirmation.
- `hosting-assistant.tsx` — NL command box, proposal cards with approve/deny,
  diagnostics.

Reuses the existing design system and console pieces — `Panel` / `Reveal` /
`SectionLabel` (`components/platform/console`), `CcCard` / `CcStat`
(`components/platform/cc-viz`), the form controls `TextInput` / `TextArea` /
`SearchField` and `Button` (`@/components/ui`), `ErrorState`
(`platform/_shared/ui`), `ChatMarkdown` for assistant prose, and `useToast` —
over the existing `http` client. States: loading, empty ("not connected" with
the connect CTA), error (`ErrorState` + retry), and per-card `unavailable` with
a reason. Upstream payloads are read defensively (`hosting-shared.tsx` readers)
so an absent field renders "not reported" rather than "undefined".

## 7. Tests

Backend (`jest`, flat `src/__tests__`): crypto round-trip + tamper + mask;
catalogue ⊆ spec + param parity + safety-class rules; client 429/timeout/error
mapping, no-secret-leak, param rejection; operations plan/execute gating
(destructive needs plan + typed confirm, single-use, expiry, params re-resolved
from the stored plan); assistant (not configured → 503, invented op rejected, no
token in prompt); route mount guards + audit coverage.

Frontend (`vitest`): the command-centre IA still holds with the new tab
(`platform-modules.test.ts`, including the `?tab=hosting` deep link); the API
surface snapshot picks up the 18 endpoints (`api-shape.test.ts`); and the new
panels are held to the tree-wide ratchets they land inside
(`palette.test.ts`, `form-platform-ratchet.test.ts`,
`silent-catch-ratchet.test.ts`), which they satisfied by using the platform
controls rather than by adding exemptions.

## 8. Out of scope / blockers to name honestly

- VPS terminal and VPS file manager: no API exists (see §2).
- Docker socket proxy on the live VPS (D6) is untouched; this module uses the
  Hostinger Docker Manager API instead, which is strictly safer.
- Live verification against the real Hostinger account requires an operator to
  paste a token into the UI (`hPanel → API`). Nothing in this repo contains one,
  and no test calls the live API.
