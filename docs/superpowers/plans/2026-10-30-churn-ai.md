# Churn AI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rank the roster by a deterministic churn score with a traceable reason and one next action per client, and let the trainer mark a client contacted or snoozed so handled clients leave the list.

**Architecture:** A pure scoring module (`churn-risk.js`) consumes the existing roster sweep for training evidence plus one uncapped `pt_clients` read for money and term dates, merged by `pt_clients.id`. A service assembles the list and applies follow-up visibility; a repository owns every follow-up statement. One on-demand AI route narrates the finished list. The frontend adds `/pt-os/clients/at-risk` and a link from the existing Today card.

**Tech Stack:** Node 22 + Express + PostgreSQL (backend), Jest + Supertest (backend tests), Next.js App Router + TypeScript + Tailwind (frontend), `routedChat` over OpenRouter for the single briefing call.

**Spec:** `docs/superpowers/specs/2026-10-30-churn-ai-design.md`

## Global Constraints

- One definition of "trained": `TRAINING_HAPPENED` in `modules/pt-os/client-context.js`. Use `sweepRoster()`; never query sessions for a last-trained date.
- One clock: `today()` from `lib/appTime` (`studioToday`). Every date decision — score, snooze validation, visibility — uses it. No `CURRENT_DATE` and no `new Date().toISOString().slice(0,10)` in this feature.
- Tenant scope is `organization_id` from the token (`orgIdOf(req)`). Every statement binds it.
- The client key is `pt_clients.id`. The legacy `client_id` (member id) is never used as a key here.
- Scoring codes (`silent_21`, `term_ending_7`, …) are churn's own names, not `signals[].id`. Only `never_started` is read from the sweep.
- No per-client LLM calls. One call per button press, zero on page load.
- No new npm dependency, no background job, no worker change.
- Migration number is 246; it is additive and reversible by dropping one table.
- Backend test command: `npm test -- <path>` (the npm script supplies `NODE_OPTIONS=--experimental-vm-modules`).

## Review Focus

These are the inputs the spec implies but no ordinary happy-path test exercises; each has a test in the task that owns the code.

1. `balance_amount` arrives from pg as a **string** for `NUMERIC`. Without `Number()`, `'0' > 0` is false and a real debtor silently scores 0.
2. `pt_clients.pt_end_date` is `TEXT`, not `DATE`, and can be empty or malformed. `termState()` must return `unknown`, never throw or invent a term.
3. pg returns a `DATE` (`hide_until`) as a JS `Date` in some drivers; a UTC conversion can hide a row a day late or early. The repository must return `to_char(...,'YYYY-MM-DD')` and the service must compare strings.
4. A client deleted (or moved out of the org) between the list read and the mark must 404, not create an orphan follow-up.
5. An empty roster, or a roster with nothing flagged, must answer deterministically and make **no** model call.

- [ ] **Step 3: Implement the repository**

`listRoster` selects `id, name, mobile, balance_amount, pt_end_date, status` with no `LIMIT`, `WHERE organization_id = $1 AND deleted_at IS NULL`, `ORDER BY name`.

`latestFollowups` must return `hide_until` as text (Review Focus 3):

```sql
SELECT * FROM (
  SELECT DISTINCT ON (client_id)
         client_id, outcome, to_char(hide_until, 'YYYY-MM-DD') AS hide_until,
         risk_score, note, created_at
    FROM pt_client_followups
   WHERE organization_id = $1 AND hide_until >= $2::date
   ORDER BY client_id, created_at DESC
) latest
ORDER BY hide_until, client_id
```

No `LIMIT` here: visibility must see every current mark even when more than
100 clients are hidden. The 100-row cap belongs to the response's `handled`
list, applied after visibility in the service.

`clientInOrg` is `SELECT id FROM pt_clients WHERE id = $1 AND organization_id = $2 AND deleted_at IS NULL` and returns a boolean. `create` inserts and returns the row with `to_char(hide_until, 'YYYY-MM-DD')`.

- [ ] **Step 4: Implement the service**

`buildChurnList(orgId, { today = studioToday() } = {})`:

1. `Promise.all([listRoster(orgId), sweepRoster(orgId, { today }), latestFollowups(orgId, today)])`.
2. Index `sweep.clients_detail` by `client_id`; index marks by `client_id`.
3. For each roster client: `term = termState(client, today)`, `flagRow = flagged.get(client.id)`, `never_started = Boolean(flagRow?.signals.some((s) => s.id === 'never_started'))`, then `scoreClient({ days_quiet: flagRow?.days_quiet ?? null, never_started, flagged: Boolean(flagRow), term, balance_amount: client.balance_amount })`.
4. Build the row: `{ client_id, client_name, ...result, last_session: flagRow?.last_session ?? null, days_quiet: flagRow?.days_quiet ?? null, term, balance_amount: Number(client.balance_amount) || 0, risk_increased: false }`.
5. Drop score-0 rows from both lists but count them in `assessed`.
6. Visibility: hidden when `mark.hide_until >= today` and `row.score < mark.risk_score + 15`; visible with `risk_increased: true` when `row.score >= mark.risk_score + 15`. Attach `hide_until` and `outcome` to handled rows.
7. Sort both with `rankClients`; slice `handled` to 100 **after** visibility is
   decided, so the 101st hidden client is still hidden from `rows`.
8. `bands` counts every scored row (visible + handled). `flagged` is that total.

`markFollowup(orgId, clientId, { outcome, snoozeUntil, note, today = studioToday() } = {})`:

1. `clientInOrg(orgId, clientId)` — return `null` if false (Review Focus 4).
2. `buildChurnList(orgId, { today })`; find the client in `rows` or `handled`. Return `null` if absent.
3. `create({ orgId, clientId, outcome, hideUntil: snoozeUntil, riskScore: found.score, note })` and return the inserted row.
